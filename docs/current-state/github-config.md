# GitHub Configuration

The GitHub settings for `timgladwell/violet` that this repo depends on but
cannot declare. They are changed in the repository's Settings UI (or with
`gh api`); the record of each change is the export diff, committed in a PR
that says why.

**Which file to trust:** [`github-export/SUMMARY.md`](github-export/SUMMARY.md)
is generated by `./export-github.sh` and is authoritative for *what is
configured*. This document is authoritative for *why*. When they disagree, the
export is right about the facts and this file needs updating. Rerun the export
after any change to these settings and commit the diff; `git status` afterwards
is the drift check.

The Cloudflare side of the deployment pipeline is in
[Cloudflare configuration](cloudflare-config.md).

## Branch rulesets

Production promotion depends on these
([ADR 0001](../adr/0001-releasing-to-production.md) has the reasoning and the
alternatives rejected):

| Ruleset | Branch | Rules |
|---|---|---|
| Protect `main` | default branch | PR required (merge commits only, 0 approvals) · signed commits · no deletion · no force-push |
| Protect `release` (fast-forward only) | `release` | signed commits · no deletion · no force-push |

- **No bypass actors on either, and none are possible.** App bypass actors need
  an organization; this is a user-owned repo. With no bypass, nobody — owner
  included — can rewrite either branch.
- **`release` has no PR rule.** It would block Cut Release's push, and there is
  nothing to review on `release` that was not reviewed on `main`.
- **No required status checks.** CI (lint, a11y, environment checks) runs on
  every PR but does not block the merge button; a failing check is caught by
  the reviewer, not by GitHub.
- **Classic branch protection is not used.** Everything is in rulesets.

**Changing a ruleset.** Disabling enforcement, even briefly, removes all
protection from that branch and nothing reminds you to turn it back on. The
only routine reason to do it is resetting `release`, and
[Cutting a Release](../runbooks/cutting-a-release.md#resetting-release-to-main)
has the exact commands, including the post-check that enforcement is `active`
again.

## Merge settings

Merge commits only, set both at the repository level (squash and rebase
merging are off) and in the `main` ruleset. Squash and rebase would mint new,
unsigned commits, breaking signing and the fast-forward to `release`
(ADR 0001), so keep both settings in step.

A PR's branch is deleted when it merges (`delete_branch_on_merge`). The merged
PR keeps a **Restore branch** button, and PRs stacked on a deleted branch are
retargeted to its base. `staging*` branches are never PR heads, so they are
unaffected.

## Actions

- **Default `GITHUB_TOKEN` permissions are read-only.** Each workflow that
  writes declares its own `permissions:` block (Cut Release, Draft Changelog,
  the booking check and the accessibility PR comment).
- **"Allow GitHub Actions to create and approve pull requests" is on.** Draft
  Changelog and the booking check open PRs with `GITHUB_TOKEN`, which needs it.
  `main` requires 0 approvals, so the approval half grants nothing extra today;
  if approvals are ever required, revisit this.
- **Any action may run** (`allowed_actions: all`), and SHA pinning is not
  required.
- **No Actions secrets, variables or environments.** CI loads
  `.env.local.example`, whose placeholders are enough to build and test; the
  real values live only in Cloudflare Pages.

## Cloudflare Pages integration

Cloudflare Pages builds this repo through the Cloudflare GitHub App, installed
on the `timgladwell` account with access to this repository (Cloudflare's
[Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/)
docs cover how it works). It deploys production from `release` and staging
from `staging*` branches; see [Cloudflare configuration](cloudflare-config.md)
for the build settings.

The Cloudflare export records the connection from Cloudflare's side
(`pages_project.json` → `source`: owner, repository, production and preview
branches). The GitHub side, the app's installation and which repositories it
can reach, is not exported: a user token cannot read GitHub App
installations. Check it at **Settings → Integrations → GitHub Apps** (account
settings, not repository settings). If the app loses access to this repo,
pushes stop deploying, with no error on the GitHub side.

## Security

Secret scanning and push protection are on: a push containing a recognised
credential is rejected. Dependabot security updates are off.

## Labels

`needs-andrea` marks issues that need Andrea's input (see
[CONTRIBUTING.md](../../CONTRIBUTING.md#issues)). `exploratory` marks an issue
that keeps context for unscheduled work: planned steps in the body, sub-issues
created when it is picked up. The rest are GitHub's defaults.
